# price-scanner

Сканер цен по российским магазинам электроники: собирает срез цен из каталогов,
складывает историю в SQLite, считает статистику по категориям и ищет аномалии
(подозрительно дешёвый товар и резкое падение цены относительно прошлого среза).

Главное правило проекта: **в репозитории нет выдуманного покрытия**. Парсер
попадает сюда только если его схема снята с живой витрины и закреплена фикстурой
в `tests/fixtures/`. Магазины, с которых разметку получить не удалось, тоже
объявлены — но честно отдают `unreachable` с причиной вместо придуманных цен.

## Что парсится

Четыре магазина с проверенным парсером (схема снята с живых витрин 2026-10-23,
фикстуры лежат в `tests/fixtures/`):

| Магазин | Как добываются данные | Чем ограничено |
| --- | --- | --- |
| **DNS** (`dns`) | HTML каталога, SSR — цена прямо в разметке карточки | С датацентрового IP витрина отвечает **HTTP 401**; нужен residential-IP или `--fetcher browser` |
| **Ситилинк** (`citilink`) | JSON из `<script id="__NEXT_DATA__">` на странице каталога | SSR отдаёт только ~8 товаров на страницу; глубокий скан требует `POST /graphql/` с живой браузерной сессией — не реализовано. С датацентрового IP — **HTTP 429** |
| **М.Видео** (`mvideo`) | Публичный BFF JSON API: `search` → `prices` → `product-details` | Работает на обычном `requests`, нужны только cookie города. Имя товара отдаётся **по одному id за запрос** (пакетного роута нет), поэтому обход 30 товаров — это 30+ запросов. Поиск нечёткий: по «видеокарта» приезжают видеоняни, мусор отсекается `min_price` |
| **XCOM-SHOP** (`xcom`) | HTML каталога (Bitrix), цена и артикул в `data-`атрибутах | Город берётся из поддомена (по умолчанию Екатеринбург) |

Что из этого **реально работает с датацентрового IP** (проверено 2026-10-23):
`mvideo` — 30 товаров, `xcom` — 24 товара. `dns` и `citilink` разбираются
корректно (это закреплено тестами на фикстурах), но сама выдача блокируется
антиботом — с другого IP или через `--fetcher browser` они оживают.

### Что не парсится и почему

Эти магазины объявлены в реестре, но парсера у них нет: разметку не удалось
получить при зонде 2026-10-23 с датацентрового IP (OVH). Селекторы «по памяти»
не пишутся принципиально — это обещание покрытия, которого нет.

| Магазин | Что ответила витрина |
| --- | --- |
| Ozon | Соединение не устанавливается: read timeout по HTTP, `chrome-error` в браузере |
| Wildberries | `search.wb.ru` → HTTP 403 (`Server: wbaas`) и по HTTP, и из браузера; сайт пишет «Возможно, нужно выключить VPN» |
| Яндекс Маркет | HTTP 403 с заголовком `X-Yandex-Captcha`, в браузере TimeoutException |
| Мегамаркет | Слайдер-капча servicepipe вместо каталога |
| Эльдорадо | HTTP 503 + JS-челлендж Group-IB на всех путях, включая `/bff/products/v2/search` |
| Регард | Read timeout по HTTP, `chrome-error` в браузере — хост не отвечает с этого IP |
| СП-Компьютер (Екб) | Read timeout по HTTP с этого IP |
| Маркет-Проф (Екб) | Read timeout по HTTP с этого IP |

При сканировании такой магазин не ломает обход: он попадает в отчёт со статусом
`unreachable` и этой самой причиной.

### Чего инструмент не знает

- **Филиал.** Ни одна из четырёх проверенных витрин не называет в каталоге
  конкретный магазин, где лежит товар. DNS отдаёт только число магазинов города,
  XCOM — общий остаток по складам, Citilink — филиал лишь для «избранных»
  магазинов авторизованного пользователя. Поэтому `branch` остаётся `unknown`, а
  не заполняется догадкой.
- **Наличие у М.Видео.** В ответах BFF `search`/`prices` его нет — `available`
  остаётся `None` (в отчёте `unknown`).
- **Сопоставление товаров между магазинами.** История ведётся по
  `product_key = магазин:артикул`; один и тот же ноутбук в DNS и Ситилинке —
  две разные позиции. Статистика считается по категории, а не по модели.

## Установка

```bash
git clone https://github.com/NeoXider/price-scanner.git
cd price-scanner
pip install -e .
```

Нужны Python 3.11+, `requests` и `beautifulsoup4`. Браузерный загрузчик —
опционально, он нужен только витринам за JS-челленджем:

```bash
pip install -e ".[browser]"
playwright install chromium
```

## Как запускать

```bash
# какие магазины есть и как они добывают данные
python -m pricescanner.cli scan --list

# один магазин, без записи в БД, с отчётом в markdown
python -m pricescanner.cli scan --store mvideo --category noutbuki --no-store --report report.md

# все проверенные магазины, запись среза в историю
python -m pricescanner.cli scan --category noutbuki

# статистика по категории (последний срез) и по товару (вся история)
python -m pricescanner.cli stats --category noutbuki
python -m pricescanner.cli stats --product dns:5633157

# аномалии в последнем срезе относительно предыдущего
python -m pricescanner.cli watch --category noutbuki

# отчёт из БД, без обхода магазинов
python -m pricescanner.cli report --category noutbuki --out reports/report.md
```

Полезные флаги `scan`: `--pages N` (сколько страниц каталога брать),
`--fetcher http|browser|local`, `--local-dir DIR` (прогон по заранее сохранённым
страницам, без сети), `--all-stores` (включая магазины без парсера),
`--format md|json|csv`, `--db PATH`.

`md` — сводка (магазины, статистика, аномалии); полный список товаров — в `json`
и `csv`.

Коды возврата: `0` — хотя бы один магазин ответил, `1` — не ответил никто,
`2` — ошибка в аргументах.

### Правила аномалий

- `below_median` — цена ≤ 20% медианы своей категории (`--median-ratio`).
  Медиана считается строго внутри категории и только если в ней набралось
  ≥ 5 цен (`--min-points`) — иначе медиане нельзя верить.
- `price_drop` — цена упала на ≥ 80% относительно прошлого известного значения
  этого же товара (`--drop-ratio 0.2` поймает и падение на 20%).
- Всё дешевле 1000 ₽ игнорируется (`--min-price`), чтобы аксессуары не засоряли
  отчёт.

Правила независимы: один товар может попасть в отчёт дважды с разным
объяснением.

### Где лежат данные

`data/prices.db` — SQLite с таблицами `prices` (каждый срез каждого товара) и
`scans` (журнал обходов, включая неудачные с причиной). В git не попадает.

## Как добавить магазин

1. **Снять разметку с живой витрины.** Сохранить ответ каталога в
   `tests/fixtures/<store>_<category>.html` (или `.json`). Без фикстуры
   парсер в репозиторий не берётся.
2. **Написать адаптер** в `pricescanner/stores/<store>.py` — наследник
   `StoreAdapter` с `name`, `display_name`, `method`, `categories`,
   `catalog_url()` и `parse()`. `parse()` обязан быть чистой функцией от текста
   страницы: именно это позволяет проверять его без сети. На мусорном входе он
   должен вернуть `[]`, а не падать.
3. **Заполнить `Placement`** только тем, что витрина реально отдала. Чего нет —
   оставить `unknown`.
4. **Зарегистрировать** класс в `pricescanner/stores/__init__.py` и поставить
   `verified = True`.
5. **Добавить тест** в `tests/test_parsers.py`: количество товаров, цены,
   наличие, ссылки — по фикстуре. Общие параметризованные тесты подхватят
   магазин сами, если дописать его в `HTML_STORES`.
6. Если разметку получить не удалось — не выдумывать селекторы, а завести
   запись в `pricescanner/stores/unverified.py` с `probe_result`: что именно
   ответила витрина.

Если витрина ходит в несколько роутов (как М.Видео), переопределяется `scan()`,
а `parse()` остаётся заглушкой — см. `stores/mvideo.py`.

## Тесты

```bash
python -m pytest tests -q
```

140 тестов, все на фикстурах и временных SQLite — сеть не трогают.

## Ограничения, о которых стоит знать

- Антибот решает, что вы увидите. С датацентрового IP половина витрин
  недоступна; `--fetcher browser` помогает не всегда.
- Схемы витрин живут месяцами, не годами. Если парсер вернул 0 товаров, а
  страница отдалась — разметка поехала, нужно обновить фикстуру и селекторы.
- Цены собираются для анализа; это не прайс-агрегатор и не средство
  автоматических закупок.
